# Стенд

Тестовая сеть для разработки. Устройства эмулируются контейнерами, но SSH и команды
у них настоящие, вендорские. Физическое железо не нужно.

Три производителя: коммутаторы Nokia SR Linux, маршрутизаторы FRRouting и
точки доступа OpenWrt. Плюс две рабочие станции Alpine Linux.

## Топология

```
                     core1
       e1/1 /    e1/2 |    e1/3 \    e1/4 \
           /          |          \        \
        acc1 ------- acc2       edge1    edge2
       /  e1/2  e1/2  |  \
  e1/3/  \e1/4        |   \e1/4
    pc1  ap1       e1/3   ap2
                    pc2
```

| Узел  | Адрес         | Что это        | Тип на карте  |
|-------|---------------|----------------|---------------|
| core1 | 172.20.20.11  | Nokia SR Linux | коммутатор    |
| acc1  | 172.20.20.12  | Nokia SR Linux | коммутатор    |
| acc2  | 172.20.20.13  | Nokia SR Linux | коммутатор    |
| edge1 | 172.20.20.21  | FRRouting      | маршрутизатор |
| edge2 | 172.20.20.22  | FRRouting      | маршрутизатор |
| ap1   | 172.20.20.31  | OpenWrt        | точка доступа |
| ap2   | 172.20.20.32  | OpenWrt        | точка доступа |
| pc1   | 172.20.20.101 | Alpine Linux   | не на карте   |
| pc2   | 172.20.20.102 | Alpine Linux   | не на карте   |

Вход на коммутаторы `admin` / `NokiaSrl1!`, на маршрутизаторы `admin` /
`Lab12345!`, на точки доступа `root` / `Lab12345!`.

Рабочие станции на карту не идут: SSH на них не поднят, а продукт ищет
устройства по открытому порту 22.

## Требования

Linux с ядром 5.x или новее, Docker, containerlab 0.78 или новее, 6 ГБ свободной
памяти. На macOS containerlab не работает, ему нужны сетевые вызовы ядра Linux.

```shell
curl -sL https://containerlab.dev/setup | sudo -E bash -s "all"
```

Скрипт ставит Docker и containerlab. Если apt-репозиторий containerlab недоступен,
пакет берётся с GitHub:

```shell
curl -sLO https://github.com/srl-labs/containerlab/releases/latest/download/containerlab_0.78.0_linux_amd64.deb
sudo dpkg -i containerlab_0.78.0_linux_amd64.deb
```

Для донастройки коммутаторов нужны `sshpass` и `nc`.

## Запуск

```shell
sudo ./up
```

Поднять заново после правок, остановить и удалить:

```shell
sudo ./down && sudo ./up
```

## Как устроен стенд

Настройка устройства распадается на три момента времени, и `up` идёт по ним
по очереди.

**Сборка.** Обход папок стенда, и в каждой, где лежит `Dockerfile`, собирается
образ. Имя образа выводится из имени папки: `frr` даёт `netmap-frr:latest`, и
под этим именем узел объявлен в `netmap.clab.yml`. У Nokia `Dockerfile` нет,
образ готовый с ghcr.io, папка на этом шаге пропускается.

**Развёртывание.** `containerlab deploy`. Здесь задаётся всё, что можно задать
в момент создания контейнера: MAC-адреса через `exec` и стартовая конфигурация
через `startup-config`.

**Донастройка.** Обход папок ещё раз, и в каждой, где лежит исполняемый `post`,
он запускается. Шаг нужен для того, что нельзя сделать раньше, и таких вещей
две. Интерфейсы на SR Linux включаются только через `commit` в его командной
строке, а она отвечает не сразу. И lldpd на FRRouting и OpenWrt приходится
перезапускать, потому что линки между контейнерами containerlab подключает уже
после их старта.

`up` про вендоров ничего не знает, он только обходит папки. Добавить
производителя означает завести папку, править `up` не нужно.

### Папка вендора

Четыре необязательных элемента, любого может не быть:

| Файл         | Когда нужен                                                |
|--------------|------------------------------------------------------------|
| `Dockerfile` | образ собирается на месте, а не берётся готовым             |
| `start`      | точка входа образа, поднимает SSH и LLDP                    |
| `lldp`       | запуск и настройка lldpd, лежит внутри образа               |
| `*.cfg`      | стартовая конфигурация, на неё ссылается `netmap.clab.yml`  |
| `post`       | что доделать после того, как контейнеры уже связаны линками |

### nokia/

Образ готовый, `ghcr.io/nokia/srlinux:latest`. Узел занимает около полутора
гигабайт памяти, и это ограничивает размер стенда сильнее всего: три коммутатора
съедают примерно 4,5 ГБ. Довести парк до сотни устройств одними коммутаторами
Nokia нельзя, это потребовало бы 150 ГБ.

`lldp.cfg` включает объявление адреса управления в LLDP. У SR Linux оно выключено
по умолчанию, а без него сосед опознаётся только по имени, то есть уже после
входа на него. Настоящее оборудование в сети управления обычно адрес объявляет,
поэтому стенд ведёт себя так же. Сам LLDP включать не надо, он работает из
коробки.

`post` включает интерфейсы. Пока они выключены, LLDP молчит и соседей не видно,
то есть без этого шага карта в продукте останется пустой. Команды подаются
`commit save`, а не `commit now`: правка пишется не только в running, но и в
стартовую конфигурацию, иначе интерфейсы гаснут при каждом перезапуске
контейнера. Свежеразвёрнутый узел принимает команды не сразу, пока идёт
применение стартовой конфигурации ответом будет `commit already in progress`
или `Server timeout`, поэтому `post` повторяет попытку.

MAC-адреса коммутаторов задаются в `netmap.clab.yml` через `exec`, из диапазона
Nokia `90:EC:E3` по реестру IEEE. По умолчанию контейнер получает адрес Docker
с локальным префиксом `02:42`, а по такому адресу производителя не определить.
Продукт узнаёт вендора по MAC ещё до входа, и на живом железе адрес вендорский,
так что без этой подмены стенд вёл бы себя не как настоящая сеть.

Маршрутизаторам и точкам доступа адрес не подменяется намеренно. FRRouting и
OpenWrt это программные системы, своего диапазона в реестре IEEE у них нет, а
брать чужой значило бы выдавать одно железо за другое. До входа такое устройство
остаётся без производителя, как и любое с локально назначенным адресом, а после
входа вендора называет драйвер.

### frr/

Базовый образ отдаёт только демоны маршрутизации, поэтому в `Dockerfile`
доставляются сервер SSH и lldpd. Своей командной оболочки поверх не строится:
продукт обращается к устройству его же родными командами, `vtysh` для
маршрутизации и конфигурации, `lldpcli` для соседей. Так же с этим стеком
работают и настоящие сетевые ОС. В `/etc/frr/vtysh.conf` пишется
`service integrated-vtysh-config`, без него vtysh ругается на каждую команду,
хотя и выполняет её.

Узел занимает около 12 МБ памяти против полутора гигабайт у Nokia SR Linux,
что и позволяет держать на стенде больше устройств.

`start` поднимает sshd, потом зовёт `lldp`, потом отдаёт управление штатному
запуску FRR.

`lldp` перезапускает демон и настраивает его. Ключи `-c -e -s` включают приём
CDP, EDP и SONMP, то есть соседей, объявляющих себя не только по LLDP. Ключ
`-I 'eth*'` ограничивает демон интерфейсами, которые подключает containerlab,
чтобы он не следил за теми, которые заводит и правит zebra. Управляющий адрес
lldpd объявляет сам, по нему продукт привязывает соседа к найденному устройству
ещё до входа на него. Сокет lldpd создаётся под root, а спрашивает соседей
`admin`, поэтому группа сокета меняется на `frr`. По умолчанию lldpd называет
порт MAC-адресом, а сосед объявляет имя интерфейса, и продукт получает одну и ту
же связь с двух сторон разными концами и рисует её дважды, поэтому порт
переключается на `ifname`.

Базовый образ берётся с quay.io и с указанием версии. Это важно: в Docker Hub
образ `frrouting/frr` заброшен, последняя сборка там v8.4.1 от декабря 2022 года
на Alpine 3.16, снятой с поддержки. Вместе с ней приезжает lldpd 1.0.14, который
в этом окружении случайно зависает: процессы живы, кадры не отправляются,
соседей ноль, и маршрутизаторы пропадают с карты. Разовой проверкой это не
ловится, потому что сосед держится в таблице ещё две минуты после того, как о
нём перестали объявлять. Судить надо по счётчику отправленных кадров в
`lldpcli show statistics`, сравнивая два замера с интервалом. На quay.io образы
обновляются, там Alpine 3.22 и lldpd 1.0.19, и этой беды нет.

`post` не перезапускает демон вслепую. Он проверяет, видит ли узел соседей, и
перезапускает `lldp` только если не видит, до трёх попыток, а не добившись —
падает с ошибкой, чтобы стенд не поднимался молча наполовину. Список узлов он не
знает, а находит их фильтром по образу, поэтому при добавлении маршрутизатора в
топологию править его не нужно. Такой же `post` есть у OpenWrt.

### openwrt/

Сервер SSH в образе уже есть, это dropbear. В `Dockerfile` доставляется только
lldpd, без него устройство видно на карте, но без связей. Узел занимает единицы
мегабайт памяти.

Командной строки в духе `show` у OpenWrt нет и не было: система настраивается
через `uci`, а сведения о себе отдаёт через `ubus`. Драйвер продукта обращается
именно к ним, а не к выдуманным командам. Поэтому `start` первым делом поднимает
`ubusd`, без него `ubus call system board` молчит.

Пароль кладётся хешем прямо в `/etc/shadow`: `chpasswd` в busybox нет, а `passwd`
спрашивает пароль с терминала. Стенд, пароль открытый.

`start` поднимает `ubusd` и dropbear, потом зовёт `lldp`. `post` устроен так же,
как у FRRouting, и проверяет, что демон видит соседей.

`configure lldp portidsubtype ifname` нужен по той же причине, что и в образе
FRRouting: иначе связь задваивается на карте.

Три строки в `lldp` лечат поведение демона, каждая по своей причине.

`configure system interface pattern "eth*"` нужен потому, что OpenWrt задаёт
lldpd шаблон интерфейсов из своей сетевой конфигурации, а там логические имена
вроде `lan`. На стенде сетей OpenWrt нет, интерфейсы приходят от containerlab
как `eth1` и дальше, под шаблон не подходит ни один, и демон работает, не взяв
ни одного интерфейса. Задать то же самое ключом `-I` при запуске не выходит,
конфигурация OpenWrt его перебивает.

`configure system hostname` нужен потому, что в образе OpenWrt имя системы
осталось от машины, на которой его собирали, и lldpd объявляет соседям её.
Без этой строки обе точки доступа приходят на карту под именем
`buildkitsandbox`. Имя, которое задал containerlab, лежит в ядре, оттуда и
берётся. Описание системы содержит чужое имя по той же причине и задаётся
следом.

Контейнер держится `tail -f /dev/null`, демоны ушли в фон.

## Особенности, влияющие на код

**LLDP отдаёт соседей и по сети управления.** Все устройства стоят в одной сети
управления и видят там друг друга. Без фильтрации карта превращается в сетку, где
каждый соединён с каждым. Физические линки это `ethernet-*` у Nokia и `eth1` и
дальше у FRRouting и OpenWrt, а `mgmt0` и `eth0` это управление.

**SR Linux не принимает несколько команд через `;`.** Команды подаются потоком
на вход, по одной в строке.

**Dropbear отдаёт двоичные данные сразу за строкой опознания.** Продукт читает
приветствие SSH при обходе сети, и вместе с ним прилетал обмен ключами с нулевыми
байтами, на которых падал весь обход. Разбирается это в `scanner.py`: берётся
только первая строка, как и требует RFC 4253.

## Что делать, если

**Стенд поднят, а карта пустая или связей на ней меньше, чем должно быть.**
Обе причины лежат в фазе донастройки: интерфейсы на коммутаторах включает
`nokia/post`, lldpd на маршрутизаторах и точках доступа перезапускают `frr/post`
и `openwrt/post`. Если `up` отработал не полностью, проверять надо это:

```shell
sshpass -p 'NokiaSrl1!' ssh admin@172.20.20.11 'show system lldp neighbor'
```

Должно показать acc1 на `ethernet-1/1`, acc2 на `ethernet-1/2`, edge1 на
`ethernet-1/3` и edge2 на `ethernet-1/4`.

**Виртуальная машина была приостановлена.** Приостановка это не перезагрузка,
пересоздавать стенд не нужно. Контейнеры остаются работать, `sshd` внутри них
жив. Но мост сети управления теряет адрес IPv4, остаётся только link-local IPv6.
Хост оказывается вне `172.20.20.0/24`, поэтому устройства не пингуются и не
отвечают по SSH, хотя `docker ps` показывает их работающими. Возвращается одной
командой:

```shell
sudo ip addr add 172.20.20.1/24 dev br-$(sudo docker network inspect netmap-mgmt -f '{{.Id}}' | cut -c1-12)
```

Интерфейсы на устройствах при этом остаются включёнными, заново их поднимать не надо.

**Хост перезагружали.** Тогда пропадает сетевое окружение контейнеров и SR Linux
начинает падать по кругу. Лечится только пересозданием: `sudo ./down && sudo ./up`.

**Правили стартовую конфигурацию, а она не применилась.** Обычный `destroy` без
`--cleanup` оставляет каталог `clab-netmap/`, в нём лежит сохранённая конфигурация
каждого узла. При следующем развёртывании SR Linux загрузится из неё, а
containerlab решит, что конфигурация уже есть, и стартовую не применит. Правка
молча не сработает, хотя команды отработают без ошибок. `down` вызывает
`destroy` с `--cleanup` именно поэтому.

**Docker Hub отвечает 429.** Анонимные загрузки с адресов дата-центров упираются
в лимит, и сборка встаёт на первом же `FROM`. Лечится зеркалом в
`/etc/docker/daemon.json`, после правки нужен `systemctl restart docker`:

```json
{
  "registry-mirrors": ["https://dockerhub.timeweb.cloud"]
}
```

Образ Nokia лежит на ghcr.io и лимита не знает.

**Ничего не скачивается с ghcr.io.**

```shell
getent ahostsv4 ghcr.io
```

Адреса вида `0.0.31.x` или `fd00:` означают, что DNS перехватывает прокси на хосте.
Трафик виртуальной машины идёт от процесса `vmnet-natd`, его надо пустить напрямую,
мимо прокси.

## Выводы команд

В папке `samples/` лежат настоящие выводы, снятые с работающего устройства.
Парсеры пишутся по ним, поднимать стенд для этого не нужно.
